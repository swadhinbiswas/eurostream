## Architecture

### "Why Lambda and not Kappa?"

> Kappa serves everything off the log by reprocessing. I kept two paths
> because the SLAs differ by orders of magnitude: fraud needs seconds on
> partial data, reporting needs completeness on all data. Both read the same
> log, so replay exists anyway — if the speed path ever becomes fully
> derivable from batch output, collapsing to Kappa is a simplification I've
> already isolated behind interfaces.

### "Why not just Postgres for everything?"

> The log needs append-only semantics with per-consumer offsets — Postgres
> can fake it but you end up rebuilding broker tables and vacuum tuning.
> DuckDB beats Postgres at analytical scans (columnar, vectorized) which is
> 95% of this workload. The write path is append-heavy, the read path is
> scan-heavy; neither wants row-store OLTP machinery.

### "What breaks first under load?"

> Three things in order: SQLite's single writer (~1k events/s ceiling),
> DuckDB's no-concurrent-writers model (second pipeline process), and
> per-process window state when the stream path scales past one replica.
> Each maps to a named swap — MSK/Kafka, Snowflake, Flink windows — with no
> application rewrite, which is the whole point of the interface layer.

## GDPR mechanics

### "Walk me through an erasure request end to end."

> Tombstone lands on `erasure_requests` with one identity for event_id and
> request_id. Worker executes in order: suppression registry first —
> in-memory set plus durable table so other processes see it — then Bronze
> PII columns become `<anonymized>` (rows survive for analytics shape),
> Silver customers/orders/payments deleted, Gold aggregates deleted, fraud
> alerts purged, lake re-snapshotted through the completion hook, and an
> audit record written with `sha256(request_id:customer_id)[:16]`. Latency
> goes into a histogram; breaches increment a counter against the 60-second
> SLA.

### "Why keep Bronze rows at all?"

> Article 17 requires erasure of personal data, not destruction of event
> history. Anonymizing preserves referential shape — counts still make sense
> — while the personal data is unrecoverable. It also keeps the audit story
> clean: we can show *what* happened to the subject's records.

### "How do you know erasure actually completed everywhere?"

> Two mechanisms: verification queries in the demo assert zero Gold rows,
> exactly one audit entry, and anonymized Bronze; and tests pin the cascade
> contract including restart behavior — a fresh service seeds its suppression
> set from the durable table, proving cross-process guarantees.

## Implementation judgment

### "Your fraud rules aren't ML — is that a weakness?"

> Deliberate scope. The rules demonstrate the streaming architecture with
> interpretable features (velocity, z-score, geo). The upgrade path is a
> gradient-boosted model consuming the same per-key features the scorer
> already maintains — the architecture doesn't change, only the scoring
> function does. For interviews, three rules you can defend beat one model
> you can't explain.

### "How do you test a quality gate that copies a flag?"

> You don't trust it — you falsify it. My first consent check was
> tautological: Gold mirrors `marketing_consent` into `consents_marketing`,
> so comparing them could never fail. The fix checks mirror integrity both
> directions, and the test deliberately corrupts Gold and asserts the gate
> trips. A guard you've never seen fail is decoration.

### "What would you build next?"

> Priority order: WORM sink for audit JSONL (legal defensibility), API auth
> via gateway integration, then stream-path state externalization if scale
> demands replicas. Each is bounded by an interface that already exists.
